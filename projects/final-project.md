# Финальный проект: архитектура агентной системы

## Цель

Спроектировать агентную систему под реальную задачу и защитить архитектурные решения: почему выбран такой workflow, какие инструменты нужны, где хранится состояние, как проверяется результат и где требуется человек.

## Варианты проекта

- Coding assistant для исправления багов и генерации тестов.
- Research pipeline для подготовки аналитических отчетов.
- Customer success agent для обработки сигналов риска оттока.
- QA automation agent для проверки пользовательских сценариев.
- Internal operations agent для обработки заявок сотрудников.

## Обязательный артефакт

Проект должен содержать:

- описание цели и пользователей;
- границы автономности агента;
- выбранный стек: Antigravity, LangGraph, CrewAI или комбинация;
- architecture diagram;
- state model;
- tool map с правами и рисками;
- human-in-the-loop gates;
- eval plan и acceptance criteria;
- observability plan;
- security checklist;
- rollout plan: prototype, pilot, production.

## Architecture canvas

Заполните этот canvas перед защитой:

- **User goal**: какую проверяемую цель получает агент.
- **Agent boundary**: что агент делает сам, что только предлагает, что запрещено.
- **Runtime**: где агент выполняется: Antigravity workspace, LangGraph service, CrewAI script/flow или комбинация.
- **State**: какие поля состояния нужны для прогресса, решений и восстановления.
- **Tools**: какие инструменты доступны, какие права у каждого инструмента, какие side effects возможны.
- **Human gates**: где выполнение останавливается для approval, review или escalation.
- **Verifier**: кто или что проверяет результат: тесты, правила, отдельный агент, человек, внешняя система.
- **Failure mode**: что происходит при ошибке модели, инструмента, данных или проверки.

## Рекомендуемый шаблон защиты

1. Какую задачу решает агент и почему обычного чатбота недостаточно.
2. Какие действия агент выполняет сам, а где останавливается.
3. Какие данные он хранит в state и памяти.
4. Какие инструменты использует и какие права получает.
5. Как система проверяет качество результата.
6. Какие риски есть и как они контролируются.
7. Как понять, что агент готов к pilot или production.

## Rubric оценки: 100 баллов

- Постановка задачи и границы автономности: 15 баллов.
- Архитектура workflow и выбор инструментов: 20 баллов.
- State model, память и checkpointing: 15 баллов.
- Human-in-the-loop, безопасность и права: 15 баллов.
- Evals, acceptance criteria и observability: 20 баллов.
- Ясность защиты и реалистичность rollout plan: 15 баллов.

## Acceptance checklist

Проект готов к сдаче, если на все вопросы ниже можно ответить “да”:

- У агента есть измеримая цель и definition of done.
- Выбранный фреймворк соответствует задаче, а не выбран “по моде”.
- State model покрывает прогресс, промежуточные результаты и точки восстановления.
- Каждый tool имеет назначение, права, ограничения и описание побочных эффектов.
- Опасные действия требуют human-in-the-loop.
- Есть минимум один независимый способ проверки результата.
- Описаны метрики качества, стоимости и скорости.
- Есть план безопасного pilot-запуска перед production.

## Мини-тест перед защитой

1. Где агент может нанести ущерб, если ошибется?
2. Какие действия должны требовать подтверждения человека?
3. Какой минимальный набор инструментов нужен агенту?
4. Какие метрики покажут, что агент полезен?
5. Как будет воспроизводиться и расследоваться ошибка?

## Ориентиры ответов для мини-теста

1. Агент может нанести ущерб в точках побочных эффектов: отправка сообщений, изменение данных, платежи, удаление файлов, публикации, доступ к персональным данным.
2. Подтверждения требуют необратимые, дорогие, юридически значимые и клиентские действия: платежи, массовые рассылки, production deploy, изменение прав, отправка внешних писем.
3. Минимальный набор инструментов должен покрывать только необходимые действия: чтение нужных данных, ограниченные API, проверка результата и логирование. Все остальное исключается до появления доказанной необходимости.
4. Полезность показывают task success rate, human escalation rate, time saved, cost per task, defect rate, user satisfaction и доля результатов, прошедших независимую проверку.
5. Ошибка воспроизводится через сохраненные inputs, state checkpoints, tool call logs, artifacts, версию инструкций, версию модели и решение человека на approval gate.

## Критерий успешной защиты

Слушатель не просто называет фреймворк, а объясняет trade-offs: почему такая архитектура подходит задаче, где она может сломаться и какие проверки не дадут агенту тихо сделать вредное действие.
